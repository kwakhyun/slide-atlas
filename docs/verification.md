## 재배포 후 저장 유지 확인

일반적인 저장·새로고침 검사와 구분해 다음 순서로 검증합니다.

1. 외부 PostgreSQL에 연결된 공개 서비스에서 새 데모 세션을 발급받습니다.
2. 검증용 프레젠테이션을 생성하고 제목을 수정한 뒤, 내용과 버전을 기록합니다.
3. 새로운 Vercel 운영 배포가 완료되면 같은 세션으로 프레젠테이션을 다시 조회합니다.
4. 제목, 버전, 슬라이드 수, 실제 내용과 해시가 모두 유지되는지 비교합니다.

내용 비교 과정에서 저장 직후의 응답과 DB 재조회 결과는 값이 같아도 객체 키의 순서가 다를 수 있음을 확인했습니다. PostgreSQL의 JSONB는 객체 키 순서를 보존하지 않습니다. [PostgreSQL 공식 문서](https://www.postgresql.org/docs/17/datatype-json.html)

따라서 해시를 계산하기 전에 객체의 키만 정렬하고, 배열 순서와 모든 값은 그대로 유지합니다. 해시뿐 아니라 중첩된 객체와 배열의 모든 값도 직접 비교합니다. 검증용 쿠키는 Git에서 제외한 로컬 파일에만 보관하며, 공개 기록에는 포함하지 않습니다. 실제 고객 자료나 OpenAI 호출은 사용하지 않습니다.

**검증 결과:** 서로 다른 두 Vercel 운영 배포 사이에서 프레젠테이션 2장의 제목, 버전 2, 슬라이드 내용이 모두 유지됐습니다. [검증 기록 JSON](persistence-verification.json)에 배포 ID, 확인 시점, 내용 해시와 비교 결과를 남겼습니다. 이 결과는 해당 재배포 시나리오의 보존을 확인한 것이며, 장기 가용성이나 백업 복구까지 검증했다는 의미는 아닙니다.

## 배포 중 발견하고 수정한 문제

### PostgreSQL JSONB의 이중 직렬화

로컬 PGlite에서 통과하던 데이터 접근 계층 테스트가 실제 PostgreSQL CI에서 실패했습니다. 이미 직렬화한 JSON 문자열을 `::jsonb` 파라미터로 전달할 때 PostgreSQL 드라이버가 다시 직렬화해, JSONB 객체가 아닌 JSONB 문자열로 저장한 것이 원인이었습니다.

JSON 파라미터에 `::text::jsonb`를 명시해 두 드라이버가 같은 방식으로 저장하도록 수정했습니다. 초기 데이터의 슬롯·버전·슬라이드 구조를 테스트에서 직접 확인했고, PostgreSQL 17에서도 전체 CI를 다시 통과했습니다. 같은 SQL 스키마를 사용하더라도 드라이버의 직렬화 동작은 별도로 검증해야 한다는 점을 확인했습니다.

### Vercel과 Docker의 빌드 산출물

Docker용 `output: "standalone"` 설정을 Vercel에도 적용한 첫 배포는 `.next/next-server.js.nft.json`을 찾지 못해 실패했습니다. Vercel에서는 플랫폼이 Next.js 빌드 결과를 패키징하도록 두고, 로컬·Docker에서만 standalone을 사용하도록 변경했습니다. 수정 후 운영 배포가 정상적으로 완료됐으며, 공개 URL에서 전체 E2E 검사를 통과했습니다.

두 수정은 [`8765dec`](https://github.com/kwakhyun/slide-atlas/commit/8765decef18168bff86537aadb95ecfdd698198f)에 포함되어 있습니다.
