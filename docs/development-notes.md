# 개발 판단과 검증 기록

기능별 구현 과정에서 발견한 문제, 결정 근거와 검증 결과를 기록했습니다. 커밋, 테스트와 저장소 산출물로 확인할 수 있는 내용만 포함합니다.

## 제품 범위

Slide Atlas는 AI 프레젠테이션 자체보다 그 기능을 운영하는 데 필요한 디자인 데이터 등록, 검수, 구조 검색, 생성, 편집과 평가를 하나의 흐름으로 연결한 웹 애플리케이션입니다. 문제 정의, 데이터 모델, UI, API, 데이터베이스, AI 어댑터, 테스트와 배포를 한 저장소에서 구현했습니다. 기획과 구현 과정에는 AI 코딩 도구를 사용했고, 생성 결과를 그대로 완료 근거로 삼지 않고 타입 검사, 자동화 테스트, 실제 API와 브라우저 검증으로 확인했습니다.

## 주요 판단

### 생성보다 승인된 구조를 먼저 고정

- 문제: 모델이 레이아웃까지 자유롭게 만들면 결과가 매번 달라져 검수와 재현이 어렵습니다.
- 결정: 전달 의도, 레이아웃, 슬롯과 제약을 온톨로지로 만들고 승인된 템플릿만 생성에 사용했습니다.
- 검증: 같은 슬롯 모델을 화면, SVG, PPTX와 품질 검사에서 공유하며 템플릿 버전을 결과에 기록합니다.
- 남은 한계: 실제 조직의 온톨로지 합의 비용과 템플릿 규모에서의 운영성은 검증하지 않았습니다.

### 규칙 기반 기본 모드와 제한된 AI 어댑터

- 문제: 사용자가 API 키나 비용 부담 없이 핵심 흐름을 재현해야 하지만 실제 모델 연동도 검증할 필요가 있습니다.
- 결정: 기본 모드는 결정론적 매핑으로 제공하고, OpenAI는 미리 선택된 슬롯 텍스트만 반환하도록 제한했습니다.
- 검증: 엄격한 출력 스키마, 원문 수치 검사, 요청 한도와 생성 메타데이터를 구현했습니다. 24개 합성 입력을 같은 조건으로 실행할 수 있는 평가 스크립트를 별도로 추가했습니다.
- 남은 한계: 의미 보존과 수치가 올바른 주장에 연결됐는지는 사람 평가가 필요합니다.

### 작성자 개발셋과 독립 평가를 분리

- 문제: 검색기를 조정하며 사용한 24개 질의의 개선 폭은 독립 성능이 아닙니다.
- 결정: 해당 수치를 개발셋 결과로 명시하고, 구현을 보지 않은 평가자가 완성한 데이터셋만 사용하는 홀드아웃 실행기를 추가했습니다.
- 검증: 최소 24개, 중복, 템플릿 ID, 완료 상태와 독립성 선언을 실행 전에 검사합니다.
- 남은 한계: 외부 평가자가 데이터를 완성하기 전에는 홀드아웃 점수가 없습니다.

### 검색 후보 축소와 페이지네이션

- 문제: 모든 템플릿을 애플리케이션 메모리로 읽어 순위를 계산하면 카탈로그가 커질 때 불필요한 전송과 계산이 늘어납니다.
- 결정: PostgreSQL에서 작업 공간, 상태, 의도, 레이아웃과 텍스트 후보를 먼저 줄이고, 슬롯 수를 포함한 구조 점수 계산 뒤 페이지 단위로 반환합니다.
- 검증: 후보에서 제외된 데이터가 결과에 섞이지 않는지, 총 결과 수와 페이지 경계가 정확한지 저장소 테스트로 확인합니다.
- 남은 한계: 현재 규모는 성능 한계나 인덱스 효율을 입증할 만큼 크지 않습니다.

### API와 화면 상태의 책임 분리

- 문제: 하나의 catch-all Route Handler와 Studio 컴포넌트에 변경 이유가 다른 로직이 집중돼 있었습니다.
- 결정: 리소스별 Route Handler로 분리하고 공통 세션, 오류, 요청 크기와 출처 검사를 서버 유틸리티에 모았습니다. Studio의 서버 작업과 편집 상태는 전용 컨트롤러 훅으로 옮겼습니다.
- 검증: Route Handler 타입 생성, TypeScript, ESLint, 단위·통합 테스트와 전체 브라우저 시나리오를 실행합니다.

## 배포에서 확인한 실패

PGlite와 외부 PostgreSQL의 JSON 직렬화 차이, Vercel과 Docker의 빌드 산출물 차이를 실제 CI와 배포에서 발견해 수정했습니다. 원인과 확인 절차는 [배포·검증 기록](verification.md)에 남겼습니다. 재현된 실패와 플랫폼별 차이도 운영 환경의 검증 범위에 포함했습니다.
