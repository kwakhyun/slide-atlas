# 운영자 사용성 검증 프로토콜

## 목적

자동화 테스트가 아닌 외부 참여자를 통해 템플릿 등록, 검수, 생성 워크플로우의 학습 비용과 병목을 확인합니다. 이 문서는 실행 절차를 고정하기 위한 것이며, 참여자 관찰이 끝나기 전에는 사용자 성과를 주장하지 않습니다.

## 참여자와 역할

- 구현에 참여하지 않은 3~5명을 모집합니다.
- 디자인 운영, 콘텐츠 운영, 웹 제품 운영 경험자를 우선하되 경험 수준을 기록합니다.
- 진행자는 기능 사용법을 먼저 설명하지 않고 막힌 경우에만 정해진 힌트를 제공합니다.
- 고객 정보나 회사 문서는 사용하지 않고 제공된 합성 자료만 입력합니다.

## 과제

각 참여자는 새 작업 공간에서 아래 과제를 순서대로 수행합니다.

1. PPTX 샘플을 가져와 추출 근거와 경고를 확인하고 템플릿 초안 하나를 저장합니다.
2. 초안을 검수 요청으로 전환하고 근거를 남겨 승인합니다.
3. 승인된 템플릿으로 4장 프레젠테이션을 생성합니다.
4. 제목 하나와 테마를 수정한 뒤 저장하고 PPTX로 내보냅니다.
5. 검색 실험을 실행하고 실패한 질의 하나를 찾아 설명합니다.

## 측정 기준

| 지표          | 기록 방법                                     | 완료 기준                                |
| ------------- | --------------------------------------------- | ---------------------------------------- |
| 과제 성공     | 최종 상태를 진행자가 확인                     | 필수 결과를 도움 없이 만들면 성공        |
| 완료 시간     | 과제 설명이 끝난 시점부터 측정                | 과제별 초 단위 기록                      |
| 오류와 되돌림 | 잘못 선택한 화면, 재시도, 이전 단계 이동 기록 | 발생 횟수와 원인 메모                    |
| 힌트          | 아래 고정 문구를 사용한 횟수                  | 0회가 무도움 완료                        |
| 이해도        | 종료 후 5점 척도                              | 구조, 상태, 품질 경고의 의미를 각각 평가 |

고정 힌트는 `현재 화면에서 다음 상태로 바꾸는 동작을 찾아보세요`, `상단과 하단의 상태 표시를 확인해 보세요` 두 문장만 사용합니다. 기능 위치를 직접 알려 준 경우에는 과제 성공과 별도로 `진행자 개입`을 기록합니다.

## 관찰과 인터뷰

진행자는 클릭을 유도하지 않고 발화, 멈춘 지점, 기대와 실제 결과가 달랐던 지점을 기록합니다. 종료 후 다음 질문을 같은 순서로 묻습니다.

1. 템플릿 상태가 바뀌는 흐름을 본인 말로 설명해 주세요.
2. 추출 근거와 자동 품질 경고 중 믿기 어려웠던 항목은 무엇인가요?
3. 실제 업무라면 이 결과를 저장하거나 승인하기 전에 무엇을 더 확인하겠나요?
4. 가장 오래 걸리거나 되돌아간 단계는 어디였나요?

## 결과 처리

원본 기록은 [`evaluation/user-study-results.template.csv`](../evaluation/user-study-results.template.csv)를 복사해 작성합니다. 참여자 식별 정보는 임의 코드만 사용합니다. 모든 참여자가 끝난 뒤 과제별 성공률, 완료 시간 중앙값, 힌트 중앙값을 계산하고 반복해서 등장한 문제를 심각도와 빈도로 나눕니다.

표본이 3명 미만이거나 진행자가 과반의 과제에 개입한 경우에는 탐색적 관찰로만 보고합니다. 결과를 README에 추가할 때에는 참여자 수, 모집 기준, 실행 날짜와 실패 사례를 함께 공개합니다.
